# 2026-10-10: Origin

exegenius starts from a note-taking practice and a complaint about AI-written explainers.

## The practice

At university, notes were kept as a personal wiki: markdown pages, one per concept or
result, linked to one another. A topic often ran across several pages, and some pages
covered entities that had no Wikipedia article, so the page was the only writeup. The aim
was re-entry: coming back to a cluster of topics months later and building on the notes
without going back to external references. Three properties made it work:

- **Recursive interpretability.** An unfamiliar term on a page is a link to a page that
  explains it, in the same voice and at the same level.
- **One known reader.** The pages are written for a reader with a known background (the
  author), so the level of explanation is chosen rather than averaged.
- **Own corpus.** The wiki does not have to meet an external project's notability,
  neutrality or style rules, as Wikipedia does. Nor does it collapse into one linear
  document (a Google Doc), where the only structure is the headings.

exegenius is a tool for authoring that kind of corpus and for deciding where to extend it
next.

## The complaint

The trigger was a recent AI-written explainer: "Integer multiplication below n log n"
(lowrank.github.io, latent-seminar, OpenAI-Math/109). It covers an OpenAI manuscript dated
2026-09-23 that claims a multitape Turing machine multiplying n-bit integers in
O(n (lg n)^(1−κ)) for a fixed κ > 0. What was actually wanted was a version that also
covered the "speedrun" of follow-up improvements after that result.

Pages like this read fluently but explain little. Two phrases from that page show the
pattern:

- "Intermediate arithmetic is exact on dyadic real and imaginary parts"
- "converts these through a chirp identity to convolution."

Neither "dyadic" nor "chirp identity" is defined or linked. Both have real meanings:

- "Dyadic" can mean the dyadic rationals m/2^k, which are exactly the numbers a finite
  binary expansion represents.
- The chirp identity is a specific equation, nk = (n² + k² − (k − n)²)/2. Bluestein's
  algorithm and the chirp Z-transform use it to rewrite a DFT as a convolution.

A reader who doesn't already know these cannot tell whether either phrase carries content
or is decoration. The original note called this "mannered prose" and guessed that a wiki
format would drive it out, because every term would have to point somewhere.

That guess is half right, and the wrong half shapes the design. Requiring every technical
term to resolve to a page or to a declared background item finds *ungrounded* terms. It
cannot separate a meaningful ungrounded term ("dyadic") from a decorative one. Both get
flagged, and a person or a model has to decide which is which. R1 (below) said "if the
phrase grounds to nothing, it was decoration"; "dyadic" is a counterexample.

## The reframing

The idea is to treat building a documentation corpus as a game played against a simulated
reader. A reader agent, in the style of a Deep Research agent, starts from a stated
background and a goal. It moves through the wiki and either reaches the goal or gets lost.
The author has three aims:

1. Maximise what transfers to the reader.
2. Reach each goal in the fewest hops.
3. Minimise confusion, and the potential for confusion, systematically enough that the
   result is "proof-like".

The reference that names the core difficulty is Yuan, Xiao, Li, Xuan, Tong, Diab and
Mitchell, "Towards Valid Student Simulation with Large Language Models" (arXiv:2601.05473,
January 2026). It calls the failure the *competence paradox*: when a broadly capable LLM is
asked to play a learner who knows only part of the material, it makes unrealistic errors
and learns in unrealistic ways. The paper's remedy is to treat simulation as generation
constrained by an *Epistemic State Specification* (ESS), which states three things:

- what the simulated learner can access,
- how its errors are structured,
- how its state changes over time.

The paper surveys existing work and argues a position. It does not present a system or a
benchmark.

The paradox is sharper for exegenius than for tutoring. A simulated reader asked about the
chirp identity already knows the chirp identity. "The reader understood the page" counts as
evidence only if the understanding can be shown to come from the page.

## The design conversation

Before this repository had any files, the idea went through three rounds of chat. Later
entries refer to the rounds as follows:

- **R1, a first Claude response.** It covered:
  - the objective function: reader state as in Knowledge Space Theory (KST), entry
    contracts (requires / provides / goals), shortest hop as a graph search, and confusion
    split into static and semantic parts;
  - a deterministic linter, built before any LLM is involved;
  - a closed-book simulated reader with leakage control;
  - tracking correctness separately from comprehensibility;
  - named author moves;
  - the crate split and caching of LLM calls.
- **R2, a ChatGPT response to R1.** It covered:
  - verification and discovery as separate objectives;
  - KST, then probabilistic mastery, then a POMDP, as stages of one progression;
  - keeping the planner separate from the simulator;
  - term grounding in three stages;
  - a fuller ESS and a four-test validation protocol;
  - typed relations: requires, motivates, formalizes, illustrates, proves;
  - adversarial misreading kept within explicit constraints;
  - a chirp-Z case study, three experiments, and a priority order.
- **R3, a Claude response to R2.** It argued that:
  - verification and discovery differ in how they know things, not just in purpose;
  - treating structural scores as targets produces atomisation and definition chains with
    no motivation;
  - good explanations break structural rules on purpose;
  - lint rules should be versioned hypotheses with typed exceptions and obligations, and
    never the optimisation objective.

A separate ChatGPT answer listed ten v1 priorities. 2026-10-10-v1-scope goes through them
one at a time.

The positions are recorded by topic, with their provenance, in these entries:

- 2026-10-10-reader-model: reader state, entry contracts, path planning, typed relations
- 2026-10-10-simulation-validity: ESS, leakage, validation, adversarial reading
- 2026-10-10-rules-and-grounding: lint rules, term grounding, intentional rule-breaks,
  provenance of claims, author moves
- 2026-10-10-v1-scope: what the first working version contains and how it is built
- 2026-10-10-ideas-bank: every idea from the above, each with an ID and a target (v1,
  v1-exp, later, rejected)

## Constraints set for the project

- Get to a working version quickly. v1 outputs a wiki.
- Avoid over-engineering, and avoid naive simplification.
- Ideas go into the ideas bank and form a roadmap. v1 does not have to implement them.
- Start with a Rust core crate and a Rust CLI crate. Add Python bindings later. Using one
  language early keeps iteration fast and keeps coding-agent token use low.
- Provide a CLI that a coding agent can call. Do not run a server.
- Follow the development conventions of lmmx/polars-genson (recorded in
  2026-10-10-v1-scope).
- Iterate. Nobody expects the first design to be right.
