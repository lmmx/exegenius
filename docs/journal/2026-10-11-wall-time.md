# 2026-10-11: Wall time

A run of 0.5.0 on Haiku found a concept the v0.1.0 wiki had missed, but took a long time, and then stopped partway. This entry:
- measures where the time goes, in the transcripts available and in the author's run;
- sets out the changes that could shorten a run without weakening a check;
- records the constraints of the setup they must work in.

The advice for batches over 20 and the run-to-completion rule are built (2026-10-11-graph-growth). The rest is not yet; the order of work is at the end.

## How a run is driven now

exegenius makes no model calls. A Claude Code session runs the loop the skill describes:
- **The skill.** `exegenius init` writes the skill to `.claude/skills/exegenius/SKILL.md` and nothing else under `.claude/` (exegenius-cli/src/main.rs:14-15, exegenius-cli/src/main.rs:143-146).
- **The prompts.** `next` prints one prompt per task, about 45 words of instructions around the task's paths to copy into a subagent call, followed by advice on parallelism, fresh subagents and model choice ("in Claude Code: model haiku" for readers) (exegenius-cli/src/main.rs:225-280). The session has to copy every prompt and choose every model by reading that advice.
- **The barrier.** A new batch is computed only once every task of the current batch has been accepted (exegenius-core/src/task.rs:3-5).

A run with the default configuration (`rounds = 3` audit rounds, `simulation.rounds = 2`, no ablations) passes through at most about 25 batches. In order:
1. extract;
2. argument;
3. write, then audit;
4. up to two more audit rounds, each of extend, argument (when extend changed the pages), write and audit;
5. the writes queued by the last audit round;
6. outline, overloads and support, then the writes they queue and the support recheck;
7. goals;
8. two simulation rounds of read and baseline, grade and attribute, with repair writes after the first.

Extract, extend and argument are single tasks, so nothing runs alongside them.

## What the transcripts show

The only timing data are the subagent transcripts of the demo runs made while developing 0.4 and 0.5 (demo to demo5 in the development sessions). There are 65 task subagents. Three died at an account usage limit and are left out, leaving 62. The figures use each message's timestamp. Time from a tool result to the next model message counts as model time; time from a model message to its tool result counts as tool time.

| read (haiku) | 20 | 66s | 107s | 1.1 | 92% |
| write (haiku) | 11 | 99s | 164s | 1.0 | 98% |
| write (sonnet) | 4 | 72s | 85s | 2.2 | 95% |
| audit (haiku) | 4 | 99s | 146s | 1.5 | 99% |
| argument (sonnet) | 2 | 162s | 184s | 1.5 | 98% |
| outline (haiku) | 2 | 91s | 94s | 1.0 | 97% |
| notation (haiku) | 1 | 153s | | 1.0 | 98% |
| goals (haiku, sonnet) | 3 | 32s | 61s | 1.0 | 90–94% |

| baseline (haiku) | 5 | 17s | 28s | 1.0 | 89% |

Caveats:
- The runs predate parts of 0.5. The notation task is the one the overloads task replaced.
- The haiku writes are repairs from a simulation. The sonnet writes are the relations demo, whose rejections came from the then-new relation check.
- The haiku and sonnet writes are of different pages, so the two rows do not compare the models.
- No batch had more than 15 tasks.

What the figures say:
1. **The model takes 89–99% of each task's time.** The `exegenius` commands take the rest. Nothing in the Rust code bounds wall time.
2. **Up to 15 subagents ran at once.** The subagents of each batch received their prompts within the same second, and up to 15 ran at the same time. `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY` was not set (Claude Code 2.1.296). The Claude Code docs give it a default of 10 for "read-only tools and subagents that can execute in parallel" (https://code.claude.com/docs/en/env-vars.md). That limit did not hold back the subagents of these runs, which ran in the background.
3. **The slowest task sets each batch's length.** In the three batches of 10 or more tasks, the mean task took 51%, 62% and 64% of the batch's span. For example, the batch of 10 reads and 5 baselines had a median task of 55s and a span of 107s.
4. **A rejection costs a regeneration.** Submits per task were 2.2 for the sonnet writes and 1.5 for audits and the argument, against about 1.0 elsewhere. Each extra submit means the subagent rewrites its answer, which takes 30–90s.
5. **Batches had gaps between them.** The time from one batch's last acceptance to the next batch's first subagent was 31s, 48s, 49s, 79s and 93s, and once 219s. The session driving these runs analysed results between batches, so these gaps are longer than a session that only loops would leave.

The transcripts cannot say how long a whole run takes, or what share the single-task phases take, since the demo runs were partial.

## What the author's run shows

exegenius records no times, so the only figures for the author's run of 0.5.0 are what Claude Code showed. That was Claude Code 2.1.296 on Haiku 5.5, in a podman container, with a Pro plan. When the main session stopped after the second audit round:
- **Session totals.** The session showed 3h 1m of wall time, 6h 28m of API time, and $15.21 (5.4m output tokens, 236.8m cache reads).
- **Batch sizes.** Round 2 was a batch of 82 audits. The extend after it added enough concepts that the next batch was 119 writes. 2026-10-11-graph-growth records why the graph grew and the change to the audit and extend instructions. The number of tasks, not the time each takes, was the largest term in the run's length.
- **The stop.** The main session stopped before the 119 writes, saying the work had "grown past what I can run to completion within the budget". No budget was configured. Asked, it said it had "used the word 'budget' loosely".
- **The limit.** After the author told it to continue, Claude Code refused a spawn with "Concurrent subagent limit reached. You can run 20 subagents at once. Do not retry." The session started the next writer when one finished. This is the documented limit of 20, binding on a batch of 119.

API time over wall time is about 2.1. The cost covers the subagents, and the main session's 298 requests could not fill six and a half hours, so the API time very likely sums the subagents' requests. Then on average about two model requests were in flight, during batches of 82 and 119 tasks under a limit of 20. A main session that starts a few subagents at a time, or waits long between them, would give this. The figure is an average over the whole run, single-task phases included, and the timing record would show where it comes from.

## Tokens

The author's run also hit the Pro plan's session limit. Usage counts tokens, not time, so where the tokens go matters as much as the wall time.

**What the author's run shows.**
- **Totals.** The session totals for Haiku were 236.8m cache reads, 13.0m cache writes, 1.9m uncached input and 5.4m output. Cache reads are 92% of the tokens processed.
- **Writer context.** The subagent list showed writers at 76.5k to 130.9k tokens, with activity lines such as "Reading paper.txt sections on labels" and "Reading paper.txt Lemma 6 passages".

**What the demo transcripts show** (the 65 task subagents above):
- **Fixed context.** The first request of every task subagent carried 42.5k–46.0k tokens (median 42.7k), before the subagent had read anything. Its prompt is about 830 characters, so nearly all of that is the general-purpose subagent's system prompt and tool definitions in the development environment. The size will differ in the author's environment, but every subagent pays it.
- **Task files.** Task files are small: the median write task is 6.3 KB, the median audit task 7.9 KB.
- **Cache reads.** Every turn sends the whole context again, read from the cache. The median cache reads per task were 124k for a grade (3.4 turns), 254k for a write (6.2 turns) and 518k for a read (11.8 turns).
- **Sources.** The demo's sources are short, so the demo writers read little of them.

**Why writers grow so large.** The write task lists the concept's evidence quotes without their surroundings (exegenius-core/src/write.rs:301-310), and the instructions say "read the parts you need (search for the evidence quotes)" (exegenius-core/src/write.rs:70). So each writer opens the paper and reads sections of it. What it reads stays in its context for every later turn.

The tokens of a run are therefore roughly the number of tasks, times the fixed context plus what each task reads, times its turns. Each factor has a lever:
- **The number of tasks:** the growth fix in 2026-10-11-graph-growth.
- **What writers read:** the write task could carry the paragraph around each evidence quote. exegenius already locates quotes in the sources (exegenius-core/src/text.rs), so writers would copy citations from the task file and open the paper only for what the passages lack. The risk is that writers read less around a concept than they do now. Audit gap counts on the same wiki, with and without passages, would show it.
- **The fixed context:** a subagent definition limited to reading, writing and the shell may carry less than the general-purpose subagent. How much less has not been measured.

**What happens at the limit.**
- **Failures.** Once the limit is hit, every request returns HTTP 429. Running subagents fail as their next request reaches it, so the failures arrive over minutes, not at once.
- **Nothing accepted is lost.** A task stays pending until `submit` accepts it, so `next` lists the failed tasks again. An answer file written but not submitted is overwritten by the retry.
- **Resumption.** Claude Code resumed by itself when the limit reset ("Continuing automatically at 6:20pm").
- **No sight of usage.** exegenius cannot see the account's usage. The main session's earlier stop "within the budget" was a guess made before any limit was hit.

What exegenius could show is the work ahead: `status` could give the pages and the number of tasks the next round will issue, so that the scope can be judged before a run, not after.

## The setup the changes must fit

The author runs Claude Code inside a podman container. That has three consequences:
- **No recursive calls.** Nothing inside the container can start another `claude` process. A driver that hands each task to its own `claude -p` process cannot run there.
- **Both modes must work.** Claude Code runs either interactively or headless with `claude -p`, and exegenius must work the same way in both, given only the project directory.
- **The main session drives the loop.** Parallelism comes from the subagents that one main session starts.

Three documented behaviours of headless mode bear on this (fetched 2026-10-11):
- **Fork mode is off.** Interactive sessions run subagents in the background. In `-p` it is off unless `CLAUDE_CODE_FORK_SUBAGENT=1` is set (https://code.claude.com/docs/en/env-vars.md). Foreground subagents started in one message may then be held to `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY`; this has not been measured.
- **Background work is cut off.** After its last turn, `-p` waits for background subagents for at most `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` of idle time (default 600000, ten minutes). It then stops them and drops their partial results; `0` waits indefinitely (https://code.claude.com/docs/en/headless.md).
- **Spawns past the limit are refused.** A spawn beyond `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20) fails with "Concurrent subagent limit reached" and is not queued (https://code.claude.com/docs/en/sub-agents.md). A first simulation round can exceed 20 tasks: up to 9 goals per reader profile, each with two reads and a baseline, makes 27.

The docs also say a subagent defined in `.claude/agents/` may set `model` and `tools`. A subagent other than a fork starts with the project's CLAUDE.md files and a snapshot of `git status` (https://code.claude.com/docs/en/sub-agents.md). In a wiki project, that snapshot lists the files under `docs/` and `exegenius/tasks/`. Readers and auditors are meant to see only what their task shows them.

## Changes

### 1. A timing record

The record comes first, so that every later change can be measured on a real run rather than on the transcripts above.

`next` records when it issues each task and in which batch. `submit` records every attempt, with its time, whether it was accepted, and the first line of a rejection. These go in `exegenius/timing.json`, apart from the task state. The clock is metadata only: no decision reads it.

`exegenius status --timing` would give:
- per phase and per batch, the number of tasks, the median and slowest time to acceptance, the span, and the mean task time over the span;
- the gap between each batch's last acceptance and the next issue, which is the time the main session spends between batches;
- attempts per task by kind, and the commonest rejection reasons.

The record cannot see:
- **inside a task:** model time against tool time, and when a subagent started;
- **waves:** if a concurrency limit holds tasks back, the record shows it only indirectly, as a batch whose times to first submit fall into two groups.

### 2. Subagent definitions shipped by `init`

`init` would write two definitions next to the skill:
- **`exegenius-reader`,** with `model: haiku`, for read and baseline tasks;
- **`exegenius-task`,** with `model: inherit`, for every other task.

Each carries the standard instructions (do the task in the file, write the answer, submit until accepted, reply "accepted" or the last error), so that:
- `next` prints, per task, the definition to use and a one-line prompt naming the task file. The main session writes less per batch and no longer chooses models from prose.
- The model for readers is fixed by the definition, not by whether the main session followed the advice.
- Both definitions limit the tools to reading, writing and the shell.

Readers are told to see the wiki only through `exegenius read` and `exegenius search` (exegenius-core/src/simulate.rs:71), and nothing enforces it. Whether a definition's `tools` can confine the shell to `exegenius` commands, and whether a custom definition can skip CLAUDE.md and the `git status` snapshot, is not documented. Both are to be tried. If either works, the definition enforces the readers' blindness, where today only the instruction asks for it.

Definitions in `.claude/agents/` are loaded in `-p` mode too, except under `--bare` (https://code.claude.com/docs/en/headless.md).

### 3. Concurrency settings

In the demo runs, the default limits did not bind up to 15 subagents. In the author's run, the limit of 20 bound on a batch of 119. `-p` mode, where subagents run in the foreground, has not been measured. The plan:
- **Advice that holds in either mode** (built): when a batch has more than 20 tasks, `next` and the skill say to start 20 and add one as each finishes, rather than all at once.
- **Settings.** `init` merges an `env` block into `.claude/settings.json`, keeping any existing keys. The subagent limit is now shown to bind, so this waits only on whether settings `env` reaches it. The block raises `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` and `CLAUDE_CODE_MAX_TOOL_USE_CONCURRENCY`, and sets `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` to `0` so that a headless run never drops a batch.
- **Unknowns.** The docs do not say whether variables set through settings `env` apply to Claude Code's own limits, so this needs checking in both modes. Setting the variables on the container (`podman run -e`) works whatever the answer.

More subagents at once also means more requests per minute against the account's rate limits.

### 4. One barrier fewer per simulation round

After a round's grades, the attribute tasks and the repair writes are independent:
- attribution reads only the stored runs (exegenius-core/src/aha.rs:69-109);
- `repair` reads only stuck points and key ideas (exegenius-core/src/grade.rs:178).

Today they run as two batches, one after the other (exegenius-core/src/task.rs:424-449). Issuing them together removes one barrier from every round that has repairs, with no change to what either task sees.

### 5. Issuing by dependency rather than by batch

Within a batch, the slowest task holds up work that does not depend on it:
- **Grades.** Grading goal g needs only goal g's runs and baseline.
- **Audits.** A page's audit task shows the bindings in force from every earlier page in reading order (exegenius-core/src/symbols.rs:342-349, exegenius-core/src/audit.rs:193). So page i's audit can start once pages 1 to i have no write pending, without waiting for the rest.

Three barriers are real and stay:
- extend needs every audit of a round;
- repairs need every grade;
- writes need the argument.

**The protocol change.** `next` would hand out ready tasks while others are pending, and the skill would say to run `next` each time a subagent finishes. Each task would be printed once when issued, and `status` would list the pending ones, so a task is not handed to two subagents.

**What it costs if gating is wrong.** Audit inputs are already hashed (exegenius-core/src/task.rs), so an audit issued too early is redone. A mistake costs a repeated task, never a wrong result.

**Expected gain.** The gain is bounded by how long a batch's slowest task runs past the rest, and the timing record will measure that before this is built.

### 6. Incremental argument plans

When extend adds a concept, the argument is planned again, because a plan only counts as current if it covers exactly the plan's pages (exegenius-core/src/argument.rs:246-248). The task shows the previous plan (exegenius-core/src/argument.rs:316-319), but the answer is the whole tree: 31 steps in the demo. It runs as a single task, between extend and every write of the round.

An answer that only places the new concepts, merged into the previous tree and checked as a whole by the same `check`, would shorten the output. Whether a patch format loses anything the full revision catches, such as a step the new concept should restructure, is open.

### 7. Fewer first-attempt rejections

The rejection reasons from the timing record show which checks fail first time. Worked examples in those tasks' instructions shorten the slowest tasks without relaxing a check.

## Not pursued

- **A headless driver,** one `claude -p --bare` process per task. It would skip the main session and its limits, and `--bare` skips CLAUDE.md, but the container cannot start nested `claude` processes. Starting one container per task from outside would add a container start and authentication to every task, and would make running exegenius depend on how it is hosted.
- **Fewer rounds, smaller budgets, or a smaller model for writers.** These trade quality for time, and the configuration already exposes them.

## Speed against quality: first drafts in waves

First drafts are written in one batch, so no writer of a first draft sees the bindings of earlier pages. `in_force` reads `graph.bindings` (exegenius-core/src/symbols.rs:342-349), which only `apply_write` fills (exegenius-core/src/write.rs:413-415). Clashes are caught later by audits and the overloads task, at the cost of rewrites and re-audits.

Writing first drafts in waves along the reading order would lengthen the path to the first audit but could save repairs. The comparison needs the timing record plus the counts of overload candidates and symbol gaps on the same wiki. It is a trade-off, not a speed-up, and comes after the rest.

## Order of work

1. The timing record and `status --timing`.
2. The subagent definitions, with `next` and the skill updated to use them.
3. Source passages around each evidence quote in write tasks.
4. The combined attribute and repair batch.
5. Concurrency settings from `init`, once it is known whether settings `env` reaches Claude Code's limits; the advice is built.
6. Issuing by dependency, if the timing record shows long tails.
7. Incremental argument plans, and examples for the commonest rejections.
