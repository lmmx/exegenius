# 2026-10-10: v1 scope

> Superseded in part by 2026-10-10-revised-v1-design, which wins where the two conflict.

What the first working version contains, what it leaves out, and how it is built. R1, R2
and R3 are the three design rounds described in 2026-10-10-origin. Each idea mentioned
here has an ID in 2026-10-10-ideas-bank.

## The shape of v1

v1 is a deterministic tool that an author drives:

1. An author writes markdown entries with frontmatter. The author is a person, or a
   coding agent such as Claude Code acting for one.
2. `exegenius check` reports structural defects, each with a rule ID and a suggested
   author move.
3. `exegenius plan` gives the reading path from a profile's background to a target.
4. `exegenius build` renders the corpus as a static wiki.
5. An experimental simulator is the last v1 milestone. It is labelled as such and cannot
   override `check`.

**exegenius v1 contains no LLM for generating text.** The coding agent writes the
entries, and exegenius is the instrument the agent uses to check its work. This covers
"cross-referenced explanation generation" and "structured knowledge extraction" without
putting a model, prompts, or an API key in the core. The only model calls inside
exegenius belong to the simulator. They have to be there because a closed-book reader
must be a direct API call with nothing in context except the visited pages
(2026-10-10-simulation-validity).

## The ten suggested priorities

A separate ChatGPT answer listed ten v1 priorities. Here is how each one lands:

| Priority | In v1 | How |
|---|---|---|
| Source ingestion | partly | a sources table (id, citation, URL or path); no fetching or parsing of PDFs or arXiv |
| Structured knowledge extraction | no, done by the author | the author or agent writes the frontmatter; extraction by a model inside exegenius comes later |
| Evidence and provenance tracking | yes, structurally | claim markers cite source IDs; each claim carries a status; lint checks the references |
| Concept dependency mapping | yes | declared `requires` and `provides`; `exegenius graph` exports it |
| Cross-referenced explanation generation | done by the agent | the agent writes entries guided by `check` and `plan` output and a skill file; exegenius renders links and backlinks |
| Reader goal specification | yes | `goals` in frontmatter; named background profiles |
| Explanation path planning | yes | prerequisite closure and topological order (2026-10-10-reader-model) |
| Automated accuracy validation | no | needs source text and a model; v1 shows unverified claims instead of hiding them |
| Comprehension test generation | partly | goals are authored by hand; the experimental simulator answers them; generating questions comes later |
| CLI and Claude Code integration | yes, as a CLI and a skill file | no MCP server, no daemon |

Of the ten, automated accuracy validation carries the most risk, and v1 does not attempt
it. A wiki that shows "3 claims unverified" on a page is more honest than one that runs a
weak automated check and reports a pass.

## Coding-agent integration

A coding agent can already run a CLI. Two things make the CLI agent-friendly:

- **Machine-readable output.** Every command that reports findings takes `--json` and
  emits a stable diagnostic schema: rule ID, class, severity, entry, span, message,
  suggested move. Exit codes separate "integrity errors" from "pedagogical findings only"
  and from "clean".
- **A skill file.** A `SKILL.md` documents the author loop for Claude Code: check, fix,
  plan, build, and later simulate. It lists the frontmatter schema, the rule IDs and
  their moves, and the commands. A skill is one markdown file, loaded only when relevant.

An MCP server would add a process and a protocol and give the agent no ability the CLI
lacks, so v1 has none (ideas bank: rejected for now).

## Corpus format

From R1, adjusted by 2026-10-10-reader-model:

- Plain markdown files with frontmatter, linked with `[[id]]` and `[[id|anchor]]`. git
  holds the history. The files are the source of truth, and any cache is derived from
  them.
- An `exegenius.toml` at the corpus root holds the background profiles and the sources
  table.
- Profile items are concepts with no home entry. Links to them resolve, and they render as
  plain text or as an external link if a URL is given.

A sketch of one entry and the corpus config, to steer the schema (not final):

```markdown
---
id: chirp-identity
title: Chirp identity
kind: result
aliases: [chirp trick]
requires: [dft, convolution]
provides: [bluestein-reduction]   # `id` is provided implicitly
motivates: [chirp-z-transform]
goals:
  - q: >-
      Why does nk = (n² + k² − (k − n)²)/2 let a DFT of any length N be computed
      as a convolution?
    kind: transfer
    tests: [chirp-identity, convolution]
    answer:
      - substituting the identity splits ω^{nk} into ω^{n²/2} · ω^{k²/2} · ω^{−(k−n)²/2}
      - the last factor depends only on k − n, so the sum over n is a convolution
        with a chirp sequence
---

The [[dft|discrete Fourier transform]] of length N ... [^src:bluestein-1970]
```

```toml
[profiles.self]
background = ["complex-numbers", "big-o", "polynomials"]

[sources.bluestein-1970]
citation = "Bluestein, L. I. (1970). A linear filtering approach to the computation of the discrete Fourier transform. IEEE Trans. Audio Electroacoustics 18(4)."
```

The YAML frontmatter needs a parser crate. `serde_yaml` was archived by its maintainer in
March 2024, and the choices are its maintained forks or `saphyr`. TOML frontmatter (`+++`)
parsed with `toml` avoids the question, at the cost of compatibility with Obsidian and
mkdocs, which both read YAML frontmatter and `[[wikilinks]]` (open question 1).

## Wiki output

`exegenius build` writes static HTML. Each page has:

- the body, with wikilinks resolved and the anchor text kept;
- a requires/provides panel;
- backlinks;
- the goals;
- a count of unverified claims;
- the reading path from the default profile.

An index page groups entries by kind. comrak parses the markdown. Its wikilinks extension
(title after the pipe) produces link nodes in the AST, so resolution happens on the AST and
skips code spans and code blocks. The golden corpus is mathematical, so `$…$` math passes
through comrak's math extension and is rendered in the browser by KaTeX loaded from a CDN.

The alternative is to emit markdown for an mkdocs site, as polars-genson does. The
requires/provides panels, backlinks and path panels all come from the graph, so they would
need an mkdocs plugin or pre-generated markdown either way. Rendering directly from the
binary keeps v1 to a single executable with no Python step (open question 2).

## CLI surface

| Command | Does | Milestone |
|---|---|---|
| `exegenius check [DIR] [--json]` | loads the corpus, runs the rules, exits non-zero on integrity errors | M1 |
| `exegenius plan TARGET --profile P [--json]` | prints the ordered reading list to an entry or goal, with hop count and token estimate | M2 |
| `exegenius graph [--format dot\|json]` | exports the concept and entry graph | M2 |
| `exegenius build [--out DIR]` | renders the wiki | M3 |
| `exegenius sim goals --profile P [TARGET]` | runs the experimental closed-book goal answering | M5 |

## Crates

| Crate | Contents | When |
|---|---|---|
| `exegenius-core` | corpus loading, frontmatter, registry, wikilink resolution, graph (closure, topological order, SCCs), rules, planning, HTML rendering; pure and deterministic | v1 |
| `exegenius-cli` | clap front end, binary `exegenius`, JSON and human output | v1 |
| `exegenius-sim` | provider trait, one Anthropic implementation, call cache, closed-book goals, baseline, span check | v1-exp |
| `exegenius-py` | pyo3 and maturin bindings over core | later |

Rendering lives in core as a module. It is deterministic and needs the graph, and a third
crate would add a boundary for nothing at this stage. The dependencies proposed for v1 are
comrak, serde, a YAML or TOML parser, petgraph, clap and serde_json, with insta,
assert_cmd, predicates and tempfile as dev dependencies.

## Conventions taken from lmmx/polars-genson

Inferred from the master branch's Cargo.toml, Justfile, .pre-commit-config.yaml,
genson-cli/Cargo.toml and docs/journal/, without reading the source:

- **Workspace.** A Cargo workspace with `[workspace.dependencies]` and
  `[workspace.package]` (authors, edition, MIT licence, repository). Member crates
  inherit these with `.workspace = true`.
- **Crate names.** Crates are named `<name>-core`, `<name>-cli` and `<name>-py`. The
  Python crate uses pyo3 abi3 and maturin.
- **Build profiles.** Dev builds use opt-level 0 with debug info off. Release builds use
  thin LTO, a single codegen unit, and stripped symbols.
- **Justfile.** A Justfile is the task runner:
  - `precommit`: taplo lint and format, end-of-file whitespace, `cargo machete`,
    `cargo fmt --check`;
  - `prepush`: `cargo check`, `cargo clippy -D warnings`, `cargo doc`;
  - tests run through `cargo nextest`.
- **Pre-commit hooks.** pre-commit runs through `lmmx/just-pre-commit`, and
  `conventional-pre-commit` enforces conventional commit messages.
- **Tests.** insta snapshot tests, plus `assert_cmd` and `predicates` for CLI tests.
- **Releases and docs.** release-plz handles Rust releases, with cargo-binstall metadata
  on the CLI crate. A docs site is built with mkdocs.
- **Journal.** Journal entries are narrative first, followed by factual sections, with
  commit hashes and measurements cited inline.

## Milestones

| Milestone | Delivers |
|---|---|
| M0 | workspace with two crates, Justfile, pre-commit, CI running fmt, clippy and nextest |
| M1 | corpus loading, frontmatter, registry, wikilink resolution, integrity rules, `check --json` |
| M2 | pedagogical rules, `plan`, `graph` |
| M3 | `build`, the HTML wiki; **first working version** |
| M4 | golden corpus, planted-defect fixtures with insta snapshots of `check --json`, skill file |
| M5 | `exegenius-sim`, experimental |

Golden-corpus fixtures can start at M1 as test data. M4 is when the corpus is complete
enough to exercise every rule.

## Golden corpus

R1 suggested seeding from old university notes known to be good. R1's thread 6 and R2
suggested building the chirp-Z and FFT-multiplication cluster by hand.

The FFT cluster sits directly under the explainer that was actually wanted, integer
multiplication below n log n with the speedrun that followed (2026-10-10-origin). Building
it as the golden corpus therefore also makes it the first real use of the tool.

Candidate entries are listed below. Per R2, the dependency edges come from the sources,
not from this list:

- roots of unity (or a profile item)
- polynomial multiplication as convolution
- DFT
- convolution theorem
- FFT (Cooley–Tukey)
- FFT-based integer multiplication (digits as coefficients, carries, precision)
- chirp identity and Bluestein's algorithm
- chirp Z-transform
- Schönhage–Strassen (1971)
- Fürer (2007)
- Harvey–van der Hoeven, O(n log n) (*Annals of Mathematics*, 2021)
- the 2026 below-n-log-n claim, with claim status `unverified`
- the follow-ups, which need sources supplied

R2's three experiments run on this corpus and stay separate:

1. **Linter recovery.** Does the linter recover planted defects? This tests software
   correctness.
2. **Simulator validity.** Does the simulator find missing prerequisites and ambiguities
   that the author independently recognises?
3. **Learning effectiveness.** Do the repairs improve answers to transfer questions?

## Open questions for steering

1. **Frontmatter format.** YAML (Obsidian and mkdocs compatible, parser crate to choose)
   or TOML (`toml` crate, no compatibility)? Does editing in Obsidian matter?
2. **Wiki output.** Render HTML from the binary, or emit mkdocs-material markdown?
   Recommendation: HTML from the binary for v1.
3. **Golden corpus.** The FFT and integer-multiplication cluster, the old university notes
   (do they still exist, and can they go in the repository?), or both?
4. **Corpus location.** Should corpora live in this repository (`examples/<name>/`), or
   should the personal wiki live in its own repository with exegenius installed as a
   tool? Recommendation: the golden corpus in `examples/`, the personal wiki separate.
5. **Edition.** Rust edition 2021, matching polars-genson, or 2024, stable since Rust
   1.85?
6. **Binary name.** `exegenius`, or something shorter for typing?
7. **Agent integration.** Is a skill file plus `--json` the whole of the Claude Code
   integration for v1?
