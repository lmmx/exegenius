Here is what the code actually does.

- Extraction (`extract.rs`): the agent proposes concepts, prerequisite edges, supporting quotations, and a target. Code checks IDs, graph validity, cycles, and whether each quotation occurs in its specified source.
- Planning (`plan.rs`): code computes the prerequisite closure of the target, stops at concepts marked as known, and topologically orders the remaining pages. Source quotation order breaks ties.
- Argument reconstruction (`argument.rs`): a distinct task builds a tree of argumentative steps, rather than treating the prerequisite graph itself as the argument.
- Writing and auditing (`task.rs` and the relevant modules): the agent writes pages, simulated readers identify gaps, and the system uses those results to queue concepts and rewrites. Code validates the structured responses and manages the loop.&#x20;

That means your intuition about the pipeline being relatively straightforward is important: the problem isn't simply how much text can a model hold in context? The system already has a way to externalise structure, persist it, and work through it incrementally.

The harder question is what information must survive each transformation, and where can the pipeline lose it?

The extraction checks illustrate the distinction particularly well. A quotation can be verified mechanically as an exact substring of the source. But that doesn't establish that the concept attached to it is a faithful interpretation, that the prerequisite edge is justified, or that the quotation supports the eventual argument step. Those are different semantic claims. The code makes some structural properties hard invariants; other properties remain judgments made by the model.

And the separate argument task matters. A prerequisite graph answers something like what must a reader understand first? An argument tree answers how does the source get from its starting points to its result? Those overlap, but they aren't interchangeable.

This is why I think our original discussion about Wittgenstein is more interesting than a generic document-length question. Your existing experiments already investigate several stages of this pipeline. The conceptual issue is whether the decomposition preserves the right kind of structure for the source, not whether the system can manufacture a sufficiently large graph.

For a mathematical paper, the relevant structure often includes definitions, lemmas, hypotheses, and inferential steps. For Philosophical Investigations, it might instead include a sequence of examples, a temptation to make a particular inference, a counterexample, a change of perspective, and a clarification of what the original question presupposed. Forcing all of that into a conventional proof tree could itself distort the text.

So I take your point to be: we have a fairly tractable extraction-and-processing pipeline; the more fundamental question is what kind of structure it needs to extract from a source in the first place. That is a different question from how many tokens or pages the pipeline can handle, and it's the one I should have stayed focused on.
