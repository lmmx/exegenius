## 1. Does it split the source apart?

Yes, but not initially into fixed-size chunks. The source is supplied as plain-text or Markdown files under `sources/`. The extraction agent reads the source and produces a structured concept graph.

Each concept has prerequisites (`requires`) and verbatim evidence quotations. The source isn't first mechanically segmented into paragraphs and distributed to independent extraction calls. Instead, the agent is asked to read the source and identify concepts and their dependencies.

The code then checks the submitted graph for things such as:

- Unique, valid concept IDs.
- Prerequisites that refer to existing concepts.
- Cycles in the dependency graph.
- Evidence quotations that occur verbatim in the cited source.
- Whether the extraction has quoted material from enough of the source's substantive sections.

That last check matters: the system has explicit coverage diagnostics, and can reject and return an extraction for revision if its quotations miss too much of the paper's structure. But coverage is a proxy based on where quotations occur; it does not establish that all the important reasoning has been extracted.&#x20;

So extraction is a model-driven pass over the source, followed by deterministic structural and evidence checks—not a MapReduce-style system that chunks the source and merges independently extracted summaries.

## 2. What runs in parallel, and what runs serially?

The best description is a sequentially orchestrated pipeline with parallel batches of independent tasks.

### 1. Extract

Read sources → concepts, prerequisites, quotations

### 2. Background and argument planning

Establish reader knowledge; reconstruct the source's argument

### 3. Write a batch of pages

Independent page tasks can go to parallel subagents

### 4. Audit a batch of pages

Fresh reader subagents; discover gaps and missing prerequisites

### 5. Update graph and repair pages

Resolve new concepts, revise affected pages, repeat for configured rounds

Conceptual flow based on the documented task loop; it is not a literal rendering of the program's control-flow graph.&#x20;

Here's the distinction at each stage:

| Operation                    | Execution behaviour                                                              |
| ---------------------------- | -------------------------------------------------------------------------------- |
| Extract the source           | A planning-agent task; not one task per source chunk                             |
| Build the background profile | A separate task, after extraction                                                |
| Construct the argument plan  | A separate task before writing, and again when the planned pages change          |
| Write pages                  | Independent page tasks can run in parallel                                       |
| Audit pages                  | Independent audits can run in parallel, using fresh subagents                    |
| Incorporate audit findings   | Requires submitted results; new concepts and dependencies affect subsequent work |
| Rewrite affected pages       | Batched; only pages whose audit input changed need to be audited again           |
| Simulated-reader evaluation  | Separate evaluation phase, with independent reader tasks and iterative repairs   |

The CLI itself does not make the model calls. `exegenius next` emits pending tasks, an external coding agent delegates and executes them, and `exegenius submit` validates and applies their outputs. Each task is represented by input and answer files, so the external agent can work on multiple independent tasks at once.&#x20;

## 3. How does it decide which pages to create?

It doesn't just split the source into a page for every paragraph or section.

The extraction stage produces a concept graph. Given the configured target, the planner computes the concepts needed to reach that target through their prerequisite edges, excluding concepts already marked as known to the reader. It then topologically orders the remaining concepts so prerequisites come first.

Separately, the argument task constructs a tree of steps for the source's argument. Each step has a claim, a method, a motivation, and substeps. The system connects these steps to pages: a page either explains an argument step or a concept on which a step relies.&#x20;

That gives you two different structures:

- Concept graph: what the reader needs to understand, and in what dependency order.
- Argument tree: how the source proceeds from its starting points through methods and substeps towards the target.

The argument tree isn't just inferred automatically from the concept graph. It's another model-generated artefact, subject to its own structural and quotation checks.

## 4. What happens when a page is written?

A writer receives its particular page task, the relevant argument step or concept, the reader profile, and selected contextual material, including the source passages around its evidence quotations. It is explicitly told to write for the reader's next uncertainty, not to mechanically cover every item in the task.

The code checks several concrete constraints: page links must resolve; mathematical symbols must be accounted for; prerequisite relationships must be stated on the page; and prose length is bounded. These checks enforce structure and consistency, but don't prove that the explanation is mathematically or interpretively correct.&#x20;

After writing, a fresh reader/auditor task identifies points where the intended reader would get stuck. Those findings can create new concept pages, add prerequisite edges, or trigger rewrites. The process repeats for the configured number of rounds, subject to early stopping when the gaps aren't improving sufficiently.

One important detail: the documented loop leaves gaps discovered in the last audit round unresolved, because there is no subsequent round to repair them.

## 5. What does that mean for processing a long source?

There is no single model call that has to hold the entire finished wiki in its context. The system externalises its intermediate state into files and graphs, and distributes page work across tasks. That's the scalability mechanism.

But the initial extraction and argument reconstruction are still substantial global-reading tasks. The code's coverage checks can catch certain forms of omission—for example, an extraction that quotes only the introduction—but they cannot guarantee that a model has correctly identified every important claim, qualification, or inferential transition.

So the source is decomposed semantically, not simply chopped into chunks. Parallelism comes mainly after task creation, while dependency management and repair create sequential stages and feedback loops.

That's the exact architectural distinction I would keep in view: Exegenius parallelises much of the production of local explanations, but the fidelity of those explanations still depends on the global structures established by extraction and argument planning.&#x20;
