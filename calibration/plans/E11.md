# E11 (preregistered): Opus `xhigh` against Sonnet `high` above the ceiling, both with the combined instruction

**Status:** written and committed on 2026-10-15 at 00:19 UTC, after K3 was adopted (`plans/K3.md`, result at 00:15) and before any E11 run. The design is K3 (c), with the changes listed under "Changes from the K3 sketch". The pipeline default is unchanged.

## The decision it informs, and why it can change it

**The planning row of `policy.md`:** Sonnet `high` with the combined instruction, supported for this paper's argument task (E10). E11 asks whether Opus `xhigh` with the same instruction writes better plans above the rubric's ceiling, where the primary measure can no longer separate them.

**It can change the row.**
- **The planner runs once per wiki.** In cache-read tokens, an Opus `xhigh` argument run (1.7–6.9 M under E7) costs about what a Sonnet `high` run with the combined instruction does (3.2–11.0 M; E9, E10). Its price per token is higher, but it is one run per wiki, so a quality gain would not be priced out by volume.
- **There is prior reason to expect a difference.** Under E7's instructions, Opus `xhigh` beat Sonnet `high` beyond noise on F1, F4 and F8 (S3). Whether the instruction erases that gap is the open question.
- **The measure can see it.** K3 detects a single removed sub-step on a 19/19 plan (4 of 4 verdicts).
- **The outcomes map to different rows:** "O better" makes the row a proposal for Opus `xhigh`; anything else confirms Sonnet `high` and records that Opus is not worth its price on this task.

**What it does not decide:** whether the plan difference matters downstream (pages and readers), and anything beyond this paper.

**Judging, J25 (pairwise, K3's prompt and pack):**
- **The files:** 7 pairs, both orders, one Opus judge per order: **14 judgements**. Fresh seed 20261041. The position of O is A in one order and B in the other.
- **Sequential second judges:** where a pair's two verdicts disagree in direction (one for O, one for S or tie, or the reverse), one more judge in each order, **+2 per such pair, at most once per pair.**
- **The pointer prompt** is K3's ("Read the instructions in … and follow them exactly …").

**The screen is judge-free:** acceptance by `exegenius submit`, node counts and characters, and any `max_tokens` stop. A checklist batch (two judges per O plan, ~12 M) is run only if S is favoured on any extraction, to locate what O loses.

## Reading (fixed now; K3 (c) unchanged)

**Per extraction,** net = (verdicts preferring O) − (verdicts preferring S):
- **O favoured** when net ≥ 2 and O wins at least one verdict in each order. With 2 verdicts, both must prefer O; with 4, net ≥ 2 and a win in each order.
- **S favoured** under the symmetric rule.
- **Otherwise tied,** and dropped from the sign test. That includes any extraction with a reversal across orders.

**The sign test** is one-sided, with H1 "O better" fixed in advance: p = P(Bin(n, ½) ≥ k) over the n untied extractions, of which O is favoured on k.
- **"O is better above the ceiling"** needs O favoured on at least 5 extractions and S on none (p ≤ 0.031).

**The control:** a proposal also needs the control pair tied (|net| ≤ 1). If it is not tied, two runs of one configuration differ as visibly as O and S, and an Opus repeat is preregistered here before any proposal.

**The smallest claimable difference** is one sub-step (K3 criterion 5). The `slight` / `clear` strengths are reported per extraction. K3 calibrates them: one constant-level sub-step drew `slight`; a 3-derivation primary gap drew `clear`.

**Same-model bias.** The judges are Opus, and so is O.
- A result that does not favour O is robust to self-preference, because the bias would push towards O.
- If O is favoured, **a Sonnet-judge cross-check is preregistered here before any proposal:** K3 (e)1's validation (6 judgements), then the 14 files judged once by Sonnet. It is flagged if the Opus and Sonnet judges' net preference for O differs in sign on 2 or more extractions.

| Outcome | Action |
|---|---|
| O better, control tied | the Sonnet-judge cross-check (above). If it holds, `policy.md` records that Opus `xhigh` is better above the ceiling at its measured cost per run, and a proposal goes to the author, who weighs the gain against Opus's price |
| O not shown better | Sonnet `high` with the combined instruction stays the planning row. Opus `xhigh` is recorded as not worth its price on this paper's argument task |
| S favoured on ≥ 5 extractions | reported, as evidence for Sonnet `high`; the checklist batch locates what O loses |
| control not tied | reported; an Opus repeat is preregistered before any proposal |

**Reported, not criteria:**
- the Bradley–Terry effect size, P(O preferred), with its bootstrap interval over extractions;
- the items each verdict decides on, and where they fall on the checklist;
- errors either plan makes;
- O's node counts and characters against S's, and the runs' cost.

## Changes from the K3 sketch, made before any E11 run

1. **The checklist sanity screen becomes judge-free and conditional** (above). Its purpose is to catch a broken O plan, which acceptance and length catch for free. The checklist is kept for the one case where it explains a result.
2. **Sequential second judges are capped at one extra judge per order per pair.**
3. **The Sonnet-judge cross-check is conditional on O being favoured.** A null result is robust to the bias it checks for.

**Not changed:** both orders on every pair, one judge per order, the per-extraction rule, the sign test, the control and the outcome table. K3 (e)4's one-order variant would be allowed by K3's numbers (0 reversals, item position share 0.50), but it would leave each extraction with a single verdict. It is not used.
